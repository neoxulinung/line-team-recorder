# LINE 團體記錄助手 — User Story

## 專案背景

這是姊妹專案，跟已經上線的「旅行規劃管理助手」（itineraryManager）系出同源：那個專案是旅遊規劃專用（固定的「時間軸／未定事項／其他資訊」文件結構），這個專案把同一套「LINE群組討論 → LLM自動整理成文件 → 指令式溯源問答」的核心概念做成通用版，讓使用者自己決定要記錄什麼主題（讀書會進度、裝修進度、專案追蹤、旅遊規劃...），整理邏輯（system prompt）可以照主題客製。

**最終目標：取代itineraryManager**。這不是一個永久並存的獨立實驗，而是itineraryManager的通用化重寫——旅遊規劃只是這個通用系統底下「客製`organize_prompt`」的其中一種用法。等這個專案做到跟itineraryManager功能對等（整理/問答/查核＋記帳/投票模組＋`/模型`＋LIFF手動編輯與版本歷史），itineraryManager這個bot就會退役，朋友群組轉來用這個。

**開發階段的關係**：即使終點是取代，開發過程仍然刻意跟itineraryManager完全平行、獨立部署，不共用資料庫/資料表，也不修改itineraryManager既有的任何程式碼——那個bot在退役之前持續有真實使用者在用，這個新專案開發期間的任何實驗或bug都不該影響到它，等這邊做到堪用了才真正切換過去。技術棧、已經驗證過的坑（Cloudflare Python Workers的Pyodide限制、`httpx2_jsfetch`的connect timeout問題等）直接沿用itineraryManager的既有經驗，不用重新踩雷——詳見`CLAUDE.md`。

**指令命名：短、通用，不特別加「主題」或「旅程」前綴**——`/整理`、`/問`、`/檢查`沿用itineraryManager現有的短指令；「開始/結束一次記錄」原本沿用itineraryManager的`/旅程 開始`/`/旅程 結束`，後來覺得「旅程」本身是旅遊語彙、跟通用化的目標矛盾，改成更中性也更好打的`/開始`／`/結束`（bare指令，不是`/旅程`的子指令）。**代價**：開發/測試期間如果同一個群組剛好兩個bot都加了，指令名稱會撞在一起（兩個bot各自獨立回應，容易搞混）——這個問題目前刻意先忽略，等真的要處理並存過渡期再回來想辦法（例如測試群組跟正式群組分開）。

## 範圍與規模

- 個人／朋友團規模使用，非多租戶SaaS，跟itineraryManager同一個規模假設。
- 開發期間**完全獨立部署**（獨立LINE Channel、Google Cloud Run、獨立D1），不跟itineraryManager共用，理由見`docs/plan.md`。
- MVP聚焦：主題建立/結束、自動整理、指令式溯源問答、查核機制。記帳/投票列為MVP後可選模組。

## 核心設計決策

### 主題生命週期
- `/開始 <名稱> [記帳] [投票]` → 開始一個新主題，下指令者成為主揪；後面接的`記帳`/`投票`關鍵字決定這個主題要不要開放這兩個可選模組（不接就是兩個都不開，之後也不能中途加開，要開別的模組就開新主題）。關鍵字用「篩掉指定字詞、剩下的當名稱」的方式解析，所以名稱本身只要不是剛好單獨一個字「記帳」或「投票」都不受影響。
- `/結束` → 只有主揪能下，停止記錄。
- 同一群組**同時最多一個進行中的主題**（跟itineraryManager的「同時最多一趟旅程」邏輯一致）。開發期間如果itineraryManager的bot恰好也在同一個群組裡、也有進行中的旅程，兩邊指令名稱相同會各自獨立觸發——這個並存期的干擾問題目前先不處理（見上方「指令命名」段落）。

### 整理prompt：只有「整理」這關需要客製，問答/查核維持通用
- 建立主題時給一個很簡單的預設整理prompt（例如「把新訊息中跟主題相關的內容整理進文件，用條列式呈現」）；如果要重現itineraryManager的旅遊規劃效果，把這個主題的整理prompt設成跟itineraryManager `organize.py`裡`SYSTEM_PROMPT`一樣的內容即可。
- 之後可以（MVP後）透過LIFF頁面的textarea編輯這個主題專屬的整理prompt——沿用itineraryManager手動編輯文件功能的同一套UI模式。
- **問答**（`/問`）、**查核**（`/檢查`）用的prompt維持一份通用版本，不因主題而異——這兩關的規則本來就跟主題內容無關（「根據文件回答」、「檢查有沒有幻覺」），只有「要整理成什麼結構」才需要因主題而異。

### 文件結構要求：只要求有標題，不強制特定章節
- itineraryManager的旅程文件強制要有`## 未定事項`這個章節（程式會解析這個標題）；通用版的主題文件沒有這個限制，因為客製化的整理prompt可能完全不會產生這種結構。
- 唯一的結構安全網：文件開頭必須是`# <主題名稱>`，避免LLM輸出整段跑掉。

### 互動方式：全部指令化，指令名稱直接沿用itineraryManager
- `/開始 <名稱> [記帳] [投票]`
- `/結束`
- `/整理` — 手動觸發整理（平常應該也會有排程自動整理）
- `/問 <問題>` — 針對這個主題的內容提問，回答附來源引用
- `/檢查` — 查核機制，列出可能沒根據的內容
- `/結算`、記帳/投票相關指令 — 只有該主題開啟對應模組時才有意義（MVP後）

### 訊息收集：跟itineraryManager各自獨立（開發期間）
- 開發/測試期間，群組裡的一則訊息如果同時有itineraryManager進行中的旅程、又有這個專案進行中的主題，兩邊會各自收一份、各自送進各自的整理流程——不需要判斷「這則訊息該歸哪邊」，因為兩套系統的資料表完全分開，各自只看自己的訊息表。等itineraryManager退役後這個問題自然消失。

## Epic A｜主題與訊息整理

- **US-A0** 作為團員，我可以用`/開始 <名稱>`開始一個新主題，我自動成為這個主題的主揪。
- **US-A0b** 作為主揪，我可以用`/結束`結束目前主題。
- **US-A1** 作為團員，主題進行中Bot會持續被動記錄群組訊息。
- **US-A2** 作為團員，系統會依照這個主題設定的整理prompt，自動把新訊息中相關的內容整理進文件。
- **US-A3** 作為主揪，我可以（MVP後）透過LIFF頁面編輯這個主題專屬的整理prompt，調整AI整理的方式。

## Epic B｜指令式溯源問答與查核

- **US-B1** 作為團員，我可以用`/問 <問題>`向Bot查詢，Bot依整理好的文件回答，附上來源引用（誰、何時提及）。
- **US-B2** 作為團員，若查無資料，Bot明確回覆「不確定/查無資料」，不能瞎猜。
- **US-B3** 作為團員，我可以用`/檢查`查看查核機制有沒有抓到可疑或沒根據的內容。

## Epic C｜LIFF頁面

- **US-C1** 作為團員，透過LIFF頁面能看到目前進行中主題的整理結果，即時更新。
- **US-C2**（MVP後）作為主揪，我可以在LIFF頁面上編輯這個主題的整理prompt。
- **US-C3**（MVP後）作為團員，我可以在LIFF頁面上手動編輯整理出來的文件內容，並看到編輯紀錄——沿用itineraryManager已經做好的「手動編輯＋版本歷史」機制。

## 可選模組（MVP後）：記帳與投票

- 開主題時用`/開始 <名稱> 記帳 投票`決定要不要開這兩個模組，開了才能用對應指令；不能中途加開。
- 功能規格（記帳分攤怎麼算、投票規則等）直接比照itineraryManager已經驗證過的Epic D／E，不重新設計，只是資料表各自獨立（`topic_expenses`／`topic_polls`等），避免共用itineraryManager既有的表。

## 待Plan階段釐清的技術問題

1. **部署拓樸**：開發期間維持完全獨立部署——Google Cloud Run（運算）＋獨立的LINE Channel／D1／R2（沿用Cloudflare帳號，但跟itineraryManager分開的資源），理由見`docs/plan.md`——等功能對等後才是「切換」而不是「共用」。
2. 資料模型：`topics`／`topic_messages`／`topic_docs`／`topic_doc_revisions`的具體欄位設計。
3. 分期規劃：Phase 1（主題建立/結束/整理/問答/查核，不含模組與LIFF prompt編輯）、Phase 2（記帳/投票模組）、Phase 3（LIFF prompt編輯、手動編輯文件＋版本歷史）的實際切法與驗收標準。
4. 主題數量/歷史主題如何管理（結束後的主題資料要不要有查詢入口，或跟itineraryManager一樣結束後LIFF資料就定格）。
5. **切換時機與方式**：功能對等後，要怎麼把朋友群組從itineraryManager轉來這個bot——是否需要搬移itineraryManager既有的旅程資料（`trips`/`messages`等）進來，還是讓itineraryManager現有的旅程自然跑完、新旅程才用這邊開始，itineraryManager單純不再開新的。
6. 指令名稱撞名（開發/過渡期兩個bot都在同一群組時）目前刻意不處理，真的要處理的話再回來這裡補決策。
